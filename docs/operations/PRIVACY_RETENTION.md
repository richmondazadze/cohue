# Privacy retention rollout and operations

Implementation source follows the lead-approved retention interpretation. Migration0002 is additive: private minimal audit, mission event high-water counter, and old-writer AFTER INSERT bridge. No public DTO/endpoint changes. Production rollout and real-runtime permission/sweeper checks are pending lead coordination; isolated PostgreSQL is not deployed deletion proof.

## Deletion behavior

The deletion transaction immediately revokes scoped owner/invitation sessions and discovery, removes capabilities/profile text, derived translation/audio, and affected cached command results. It scrubs personal commitment/proposal/response payloads, preserving original hashes/actions/timestamps in privacy_audit only. Redacted documents are private persistence tombstones; consumers exclude them rather than manufacturing new CommitmentTerms or consent hashes. Historical replay containing redacted terms returns typed NOT_FOUND. Other member room access remains possible with contract-valid “Deleted participant” role and scrubbed task descriptions, plus an explicit OPEN review. Active state/capacity stay unchanged; inactive affected plans genuinely replan or pause. Remaining active membership/reservation rows serve current operational commitments, not an indefinite public consent audit.

Cleanup is exact LIVE/SHOWCASE scope and random object IDs; another showcase session of the same principal is not revoked. Related shared proposals/tasks are conservatively scrubbed because their free text may mention the deleted person. Existing committed-event schemas already restrict payloads to opaque IDs/allowlisted action/status/code metadata; no raw names, terms, transcripts or model reasoning are retained there. They expire after720hours when rollout is enabled. Audit is restricted to opaque subject/source reference, original terms hash, action and time, expires no later than original action+720hours. No public operation reads audit. Backup retention is separate (observed TigerData3day PITR); restore must reapply deletion/revocation tombstones before public access.

The persistent sweeper repairs legacy interrupted profile deletion, expires media/receipts/sessions, prunes audit and old private source rows, and removes orphan localizations/media. Expired terminal-mission pruning uses latest recorded state history rather than creation alone. Event sequence is allocated atomically from GREATEST(counter,existingMAX)+1, so purging old events does not reset IDs. EVENT_RETENTION_READY defaults off, deliberately preventing event-history pruning during mixed old/new writers. Set to1 only after every web/worker writer is compatible; leaving it off long-term is NOT retention acceptance.

Late translation publication obtains a short mission lock AFTER provider work and rechecks current/nondeleted/redacted source before INSERT. TTS similarly locks/revalidates only after provider response. Deletion can scrub an earlier committed artifact or prevent a late artifact from publishing; provider calls are not placed under new long-held domain locks. Receipt share-link replay rechecks source access instead of restoring deleted bearer authority.

## Controlled deployment sequence (lead owns integration)

1. Preserve database backup/recovery identity and reviewed Git hash. Do not put migration administrator URI on the worker or in logs. Coordinate quiet application writes and stop existing worker; do not create a new host.
2. Apply migration0002 with administrator migration channel. Function is explicitly SECURITY INVOKER, fixed pg_catalog/pg_temp search_path, and fully qualified public.missions target. Test schemas substitute their own qualified schema. Trigger keeps counter current for old inserts during transition; it does not make pruning safe while old MAX-based writers survive.
3. Grant least-privilege runtime role access to the new private table: `GRANT SELECT, INSERT, DELETE ON TABLE public.privacy_audit TO cohue_app;`. Existing UPDATE missions and INSERT agent_events permissions support the invoker trigger. No new superuser/role/schema privilege. The private table is not exposed by a route or user-controlled SQL.
4. Using the actual runtime DATABASE_URL, run a transaction/ROLLBACK probe inserting and deleting one opaque audit row and SELECTing it; verify migration/counter trigger under runtime role. Owner-role test success cannot establish this permission. Record actual commands/result without URI/secret values.
5. Deploy compatible Vercel release and update the existing worker to the SAME reviewed commit. Verify .release-commit, Node24, systemd user/health, web release identity and no old jobs/processes/writers. Lead controls root/web deployment; backend updates worker only after exact commit authorization.
6. Enable EVENT_RETENTION_READY=1 consistently for all compatible environments, restart/redeploy as required, then run one safe labeled SHOWCASE deletion/media-expiry/sweeper scenario on deployed infrastructure with clients closed. Confirm audit expiry/pruning, source/replay/receipt denial, sequence continuity and scope isolation. No broad LIVE reset/destructive test suite.

Rollback: source rollback before0002 is structurally compatible while event pruning is OFF (trigger bridge still updates counter). Once events are pruned, do not return to MAX-only writers; use forward fix or a reviewed counter-compatible rollback. Do not undo deletion/scrubbing by restoring personal text from backup, and do not drop private audit as an ad hoc rollback. If runtime grants fail, keep worker held or fix permissions before claiming cleanup; errors/configuration alone do not prove unattended sweeps. No migration/down script or production data purge was run in this milestone.
