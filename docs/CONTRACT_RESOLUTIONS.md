# Shared contract reconciliation version 1.1.0

Implementation baseline authorized by the user on 24 October 2026 after approval of D1–D12, backend readiness and Design System v1.0. This document resolves the backend report’s elaboration gaps without changing approved architecture. Executable authority: `src/contracts/index.ts` and modules; typed request/response registry: `apiContracts`; generated navigation: `docs/API_OPERATIONS.json`; labeled fixtures: `src/fixtures`. Neither schemas nor fixtures implement authorization, database operations, matching or consent.

## Scope and reads

Every participant, mission, proposal, run, event, job, reservation and opportunity carries Scope `{executionMode:LIVE,showcaseId:null}` or `{executionMode:SHOWCASE,showcaseId:UUID}`. Derive scope from authenticated server session; never trust a caller’s mode or participantId on a business mutation. All queries, joins, indexes, receipts, caches, outbox/leases, media authorization and matching use scope. Showcase sessions can be created only for server-installed scenario IDs; only a showcase operator may submit labeled scripted scenario decisions, through the same command handlers. LIVE guest creation cannot choose an operator role. Public unauthenticated network is LIVE only; a valid showcase session may read only its own scenario. No fixture import in a live backend fallback.

Added `/api/session`, session creation, participant owner GET, scoped `/api/network`, owner-only participant inbox, creator-only mission snapshot, member room, creator replay, and authorized media. GET pagination uses opaque server-signed cursor up to 512 chars, default 30/max 100, stable `(createdAt,id)` ordering and scope/access-epoch binding. Reject tampered/stale-access cursors; they are not permission grants. Public network is an opted-in minimal graph, never Participant DTO. Inbox contains only current principal’s invitations. Preview is minimal language/expiry/access notice, no terms or profile leak. Full invitation details require redemption. Snapshot includes mission version and atomically consistent snapshotSequence; graph shares sequence. Evidence IDs are opaque references, not unrestricted fetch URLs; each detail read is scoped and permission-filtered.

Event feed is creator-only initially; narrow invitation sessions do not gain theater access. Rooms require current membership; an invitation-derived session may receive a room-scoped member capability after actual activation and membership check, never whole-profile editing or creator rights. Creator not participating may access own room as creator, explicitly checked server-side. Replay uses the same audience as snapshot and is read-only. Public network has no private mission audit feed.

On opt-out, deletion or access change, bump access epoch; re-authorize stream on reconnect and periodically during connection (at most 15 seconds). Emit only a minimal ACCESS_REVOKED control event if possible, close connection, purge affected client query/media/graph caches, and refetch safe projections. A cached receipt, cursor or event ID cannot restore revoked access.

## Matching elaborations

Version `taxonomy-1` in `src/fixtures/taxonomy.ts` is the initial confirmed skill/synonym map with English/Spanish/French aliases. Skill IDs are language independent. Unknown skills require reviewed taxonomy extension; do not silently invent coverage. User confirmation, not LLM confidence, establishes capability declarations.

Pure matching uses sorted participant UUIDs and confirmed skill IDs. Hard gates: scope, discoverability, participation opt-in, availability, active reservations, level threshold if specified, distinct-person coverage, team bounds and common overlap. Missing availability is unavailable. Creator counts only when creatorParticipates and must then be a selected member. Required HUMAN skills cannot be filled by a public resource. Exclude declined/revoked persons for that mission unless they explicitly rejoin.

Scores are integer lexicographic components, descending: (1) number of OPTIONAL requirements meeting minimum distinct coverage; (2) mutualBenefit = count of directed `(recipient,normalizedNeedSkill)` pairs satisfied by at least one other selected member (count each pair once); (3) interestRelevance = sum per member of distinct intersection between that member’s interests and the union of mission requirement skill IDs plus mission preferences; (4) preservedCommitments = unchanged, revalidated accepted members in the candidate group; then ascending teamSize and sorted UUID tuple. No weighted scores or speculative consent probabilities.

A reciprocal directed edge A→B means B offers a confirmed capability needed by A. A direct match is such a pair; a reciprocal cycle has 2–3 distinct people, including the closing edge. Canonicalize by smallest starting UUID, preserve direction, deduplicate rotational equivalents. Cycles are evidence of benefit, not implicit skill coverage/consent/activation.

Bounds: 30-fixture baseline, initial API group maximum 8 (reject larger explicitly; do not truncate), 50,000 visited search nodes, 1,500ms wall safety cap, top 5 proposals, max cycle length 3. Count a search node when visiting a partial subset in stable depth-first order. Do not use wall time in ranking or tie-break. Node-bound results are reproducible; wall cutoff depends on runtime and must be reported separately. Return complete/exhausted stats; feasible incomplete search is permitted but never advertised as optimal. NO_SOLUTION requires complete exhaustion; no feasible candidate before cutoff is SEARCH_LIMIT_REACHED, not a proof of impossibility. Tests use deterministic node budgets/clock injection.

## Capacity and D9 changes

Each participant has capacity one simultaneous commitment. On ACCEPT reserve the agreed half-open interval as ACCEPTED_HOLD until invitation expiry; activation promotes to ACTIVATED. Pending invites do not reserve. Lock participant rows in sorted UUID order within the response/activation transaction, scope reservations, reject overlapping non-released commitments in another mission with CAPACITY_CONFLICT. Exclude current mission’s own hold from conflict. PostgreSQL transaction/locking integration tests must show two simultaneous accepts cannot overbook. Live and isolated showcase capacity never overlap each other.

Before activation, profile availability/capability/opt-in edits invalidate affected proposals/checkpoints and enqueue a replan; preserve only unchanged valid accepted terms. After activation they create a review request/notice; do not automatically replan or dissolve the mission. Existing active reservation remains authoritative until an explicit authorized change resolves it. A withdrawal request is not silently ignored or automatically treated as a replacement approval: flag it prominently, stop treating the person as currently reconfirmed in UI, and preserve audit/history. Creator ACKNOWLEDGED/RESOLVED review commands record resolution only, and cannot rewrite roles/schedule/consent or release capacity by themselves. For this initial version, material active-team changes require explicit creator cancellation of that mission and a new reviewed formation; no automatic active repair. Creator cancellation releases reservations, revokes pending capabilities and records the decision; changed terms always require participant approval. This is D9’s explicit-review policy, not an added autonomous workflow.

## Receipt ordering, invitation lineage and canonical terms

On a command: validate transport/schema and authenticate current principal/scope -> locate receipt by `(scope,principal,operation,key)` -> compare canonical request digest -> return same stored result for exact replay if caller still has access -> otherwise validate current version/expiry/state/capacity and execute transaction. Same key with changed payload is IDEMPOTENCY_CONFLICT even if versions are stale. Exact successful replay does not become STALE_VERSION because its own first execution incremented the version. Revoked/deleted/session-expired access is checked before returning a receipt. Expired invitation with no prior successful accessible receipt returns 410; cancelled mission with a new command returns TERMINAL_MISSION. Do not return another principal’s receipt.

Receipt, business records and events commit together, keyed uniquely; serialize concurrent first uses, then re-read winning receipt. Expire receipts after 48h, never before the maximum command/session replay window. After expiry require a new key and current version. All mutation operations in the registry require an Idempotency-Key; body versions refer to the target record (responseVersion for invitation, expectedVersion for profile/mission/task/review).

Canonical terms are the validated CommitmentTerms object: role, responsibilities, schedule, objective/output, participant/mission and disclosed group. `canonicalTermsJson` recursively sorts object keys, NFC-normalizes strings and sorts disclosed group by participantId; preserves responsibility order. Hash UTF-8 bytes with lowercase SHA-256 on server. Revisions/translations/provider metadata do not alter the hash. Group membership/role changes DO change it; do not claim all accepted members survive replacement automatically. Carry only identical hashes with lineage source invitation/response/revision, target revision and revalidatedAt. The scope, principal and current proposal snapshot are verified independently; a hash alone grants nothing.

A redeemed session is bound to one invitation ID and scope. Superseding an invitation never silently broadens that session to another invitation; explicit new redemption is needed for changed terms. Unchanged carry-forward may expose the original receipt/lineage as read-only, but activation still validates current invitation lineage and capacity. Store token hashes server-side; DTOs/events never contain plaintext or hashed bearer material. Public GET never consumes a token. After redemption, frontend uses invitation UUID endpoints and removes token from address/history where possible. This formalizes the PRD’s suggested token/respond route into `/api/invitations/:id/respond` with scoped session authorization, avoiding bearer tokens in repeated URLs/logs.

## Event lifecycle and ordering

MISSION_CREATED uses runId:null and agent:null, state DRAFT. Mission-level human events may have null run/agent; actual AGENT/TOOL/SCOUT/EXTRACTION execution events require real persisted runId/agent. Event payloads are a strict allowlist discriminated by type. Backend validates public projections before streaming, not raw private logs. No chain-of-thought, token hashes, transcripts or tool arguments in public payloads. Event IDs and sequence are allocated transactionally; sequence starts at 1 per mission, with no duplicates. Schema version is 1, shared package version 1.0.0.

SSE `id` is sequence; `data` is one validated AgentEvent (no HTTP success envelope per frame). JSON mode uses success(EventPage). Initial snapshot/cursor is atomic; stream reads sequence > cursor, deduplicates, backfills gaps and never advances completion by elapsed animation time. Heartbeats are SSE comments, not persisted domain events. A last-event cursor conflicting with `after` is INVALID_INPUT; server never mixes modes/scopes. Current mission version prevents old event animations overwriting newer snapshots. ACCESS_REVOKED is a control meaning, not public reason details. Public graph uses only scoped safe projection; no client write of accepted state.

## Media and localization

Upload is multipart `audio` plus JSON `metadata` matching TranscriptionMetadata, not base64 JSON. Max 3,000,000 bytes audio and 60 seconds, MIME allowlist webm/ogg/mp4/mpeg/wav. Accept codec suffix only after parsing/normalizing to base MIME and validating content bytes; distrust metadata duration/size, enforce measured duration/upload cap, reject zip/HTML or polyglot content. Initial cap is below platform request limit with multipart headroom; backend must validate actual Vercel account/runtime constraints. No long-term raw upload: delete after transcription and on failure; cleanup sweeper must remove abandoned temp objects within 15 minutes. Never claim rawAudioDeleted true unless cleanup succeeded; failure returns a typed error.

Synthesis accepts authorized source ID/kind/version/hash/language, not arbitrary client terms. Gemini translation returns LocalizedText with sourceVersion and canonicalTextHash, language, originalLanguage and review status; uncertain translation requires review and never changes canonical agreement. TTS speaks only authorized reviewed text. Audio metadata exposes an authenticated same-origin `/api/media/:id` access path; raw bytes GET rechecks owner/invitation/member scope, status and expiry and returns actual audio Content-Type/no-store. API registry’s media response describes metadata for JSON Accept; audio Accept returns bytes, no JSON envelope. Never serialize vendor storage URLs or keys to public graph. READY audio needs a path; failed/expired audio has none. Synthesized TTL max 24h or source access/expiry, whichever earlier. Text-only flow has identical confirmation/consent authority. Reference transcription status is REVIEW_REQUIRED; voice never responds/launches implicitly.

## Deletion and retention

Owner DELETE participant queues deletion and immediately revokes sessions/invites/media access, removes public/discovery projection and bumps access epoch. Inactive affected missions replan or pause; active ones receive explicit privacy-safe review notice without automatic dissolution (D9). Delete profile personal fields/raw text/private media/provider caches and unused evidence within 24h. Do not retain raw audio until that deadline: D10 immediate/15-minute orphan cleanup still applies. Canonical terms containing personal text are scrubbed from general app access on deletion; retain only opaque commitment hashes, timestamps, action types and random references for a maximum 30-day minimal security/consent audit, with no display name, transcript, availability detail, IP or bearer material. These retained opaque records remain restricted personal-data-adjacent records, not claimed anonymous. Referential tombstones permit integrity without exposing identities. Clear access to existing receipts before returning any replay. Cascading provider/local object deletion and encrypted backup aging must be documented by backend; backups must not silently restore public access. No indefinite event/history retention by default. Provide visible deletion status and actual purge evidence before public use.

## Recovery and terminal policy

Creator controls start/select/activate/cancel/retry/resume, member controls assigned tasks and their own review request, operator controls dispatcher/health, authenticated invitation principal controls only its response. Backend system expiry/sweeper is not a public permission. Mission expires 24h after creation unless already ACTIVATED; invitation expires at min(created+12h,mission expiry). Guest session max24h, invitation session max12h/invitation expiry; accepted membership capability follows explicit authorized upgrade. Cancellation allowed for owned nonterminal and active missions; releases reservations and invalidates queued effects atomically. EXPIRED/CANCELLED are terminal and never retry/resume. Activated is never put back into planner by retry.

FAILED retries require a server-recorded recoverable checkpoint, <=3 attempts, input still current and remaining budgets; backoff 2/10 seconds between attempts (third failure exhausts budget). PAUSED_FOR_HUMAN resumes require an existing checkpoint and confirmed corrections/current inputs. Client provides checkpointId, not arbitrary step/state. Resume revalidates and may select a new safe checkpoint; it cannot bypass approval or inject successful outputs. Schema/semantic bad provider output gets bounded retries; missing human input pauses, not infinite retries. Leases 30 seconds, step timeout20 seconds, fence stale commits. External calls may be at least once; idempotent domain effects and usage/budget ledger remain mandatory. Deployed D7 evidence is still outstanding.

## Invitation share links (contract 1.1.0, lead continuation 25 Oct 2026)

Gap: work orders require an owner share link/QR and second-device redemption, but version 1.0.0 had no operation that disclosed a bearer token, and tokens are banned from DTOs, events and logs. Resolution: additive `issueInvitationLink` — `POST /api/invitations/:id/link`, auth OWNER, body `{rotate:boolean}`, Idempotency-Key required, 200 `InvitationLinkSchema {invitationId, token, linkEpoch, expiresAt}`. OWNER here means the mission creator or the invited participant acting from their own profile session (inbox path); an invitation-redeemed session cannot mint links. The token appears only in this response body, sent with `Cache-Control: no-store`; it never enters Invitation/Inbox/Snapshot DTOs, events, receipts or logs.

Derive the token, never persist it: `token = base64url(HMAC-SHA256(K, invitationId || ":" || linkEpoch))` with K derived from SESSION_SECRET by HKDF (label `cohue-invitation-link-v1`), so no new environment variable. Store only the token hash per invitation/epoch for preview/redeem lookup. The receipt stores linkEpoch, and exact replay recomputes the same token without retaining plaintext. `rotate:true` increments linkEpoch in the same transaction and invalidates every earlier token for that invitation; existing redeemed sessions keep their own binding until revoked by normal invitation rules. Non-PENDING, expired or revoked invitations and terminal missions return INVITATION_EXPIRED, INVITATION_REVOKED or TERMINAL_MISSION; another principal gets FORBIDDEN or NOT_FOUND. `expiresAt` equals the invitation expiry. Frontend builds `${NEXT_PUBLIC_APP_URL}/invitations/${token}` for link and QR display and keeps the token out of analytics and history as already required. No outreach is sent by the server.
