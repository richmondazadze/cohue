## Routes
| Route | What it does |
| --- | --- |
| `/` | Entry: approved proposition, Start a mission / Join, Discover–Coordinate–Make, missions started on this device. No fake network or counts. |
| `/join` | Onboarding in 4 steps (About you → Skills & needs → Time & visibility → Review). Taxonomy from `GET /api/taxonomy`; per-skill level/evidence and an explicit "I confirm" gate (sets `confirmedByUser`); needs/interests; availability intervals with explicit IANA timezone; separate unasserted participation/discoverable/public-map checkboxes. Submit = `getSession` → `createSession {LIVE}` if 401 → `createParticipant`. |
| `/me` | Participant profile + owner inbox (`inbox`, 5 s poll); per pending invitation: owner share link/QR or "Open on this device"; profile deletion (`deleteParticipant`) clears client cache. |
| `/missions/new` | Reviewed composer: optional text → `extractMission` draft (unknowns listed, creator participation never inferred); objective/output/language; requirement rows; group size, overlap, multi-day window with timezone, creatorParticipates. Validated with the shared `CreateMissionSchema`. Review step → `createMission` → `startMission` (separate keys; start failure leaves a retryable draft). |
| `/missions/[id]` | Mission Theater (creator): header with state + "Verified hh:mm:ss"; requirement rail (coverage ≠ consent); Mission / Map / Activity. Snapshot poll + JSON event cursor poll (`after`), hidden-tab pause, access-epoch/ACCESS_REVOKED purge. States: DRAFT start, PLANNING/DISCOVERING/REPLANNING current recorded step (no estimate), proposals with members/coverage/window/rationale/score/search stats and `selectProposal`, NO_SOLUTION vs SEARCH_LIMIT_REACHED copy, invitations with per-person committed status, share link + QR (`issueInvitationLink {rotate:false}`, replace link = `rotate:true` with confirm), Activate enabled only when `approvals.accepted === approvals.required > 0`, ACTIVATED → Open room, cancel sheet, terminal states. STALE_VERSION/IDEMPOTENCY_CONFLICT refetch. |
| `/invitations/[token]` | Non-consuming preview (language, answer-by, availability, bearer-link notice) → explicit "Open my invitation" (`redeemInvitation`) → `router.replace('/invitations/opened/<uuid>')` so the token leaves history. `referrer: no-referrer`, `noindex`. Token never in query keys, storage, logs or errors. |
| `/invitations/opened/[id]` | `getInvitation` (UUID): full terms (objective, output, role, responsibilities, schedule in invitation zone + viewer zone, disclosed group, terms reference, lineage), localized text toggle (translation never replaces original). Accept (terms hash + responseVersion), Decline sheet (optional reason), Suggest a change sheet (availability intervals; receipt says "not an acceptance"). Changed terms (STALE refetch) show a diff and block Accept until "I have read the updated terms". Expired/revoked/closed states. |
| `/missions/[id]/room` | `room`: Activated header, tasks first (tabs on phone), team by approved role, brief/localized briefs, public resources labeled "Public resource · Unverified", review requests. Task status `updateTask {expectedVersion}`; STALE_VERSION keeps the lost choice visible, refetches, asks to re-apply. |

## Contract / dependency questions for lead
1. No way for a session to discover its own participant id (`getSession.principalId` ≠ participant id). Frontend stores the id from `createParticipant` in localStorage per device; a `participantId` on SessionSchema (or `GET /api/participants/me`) would remove that.
2. Retry/resume need `checkpointId: Id`, but no DTO/event exposes one (`PAUSED_FOR_HUMAN.checkpoint` is a Label). Needs a field in the snapshot or event.
3. Creator theater gets participant names only from `graph.nodes[kind=participant].label`; invitation terms `disclosedGroup` has only ids + roles, and Room memberships have no display names. Confirm intended (frontend shows roles) or add display labels.
4. Invitation status per member is reconstructed from INVITATION_* events (snapshot has no invitations list); after reselection, carried-forward approvals are only visible if the server emits events for the new revision. A snapshot `invitations` summary would make this robust.
5. Redeeming in the same browser that holds a guest/owner session: does `redeemInvitation` replace the session cookie? The inbox "Open on this device" button relies on the answer.
6. `NEXT_PUBLIC_APP_URL` is used for share links unless it points to localhost (then `location.origin`), so dev links work on non-default ports.
7. Next dev/prod request logging prints `/invitations/<token>` paths server-side; backend/lead may want to redact that path in logs.
